# opencode_profile

Portable team workspace for managing code execution, project operations, and Jira or Notion reporting across data, web, and IoT projects.

## Quickstart on a new machine

Run these steps in order on any new Mac or Windows machine:

### 1. Clone this repo

```bash
git clone git@github.com:mathangspk/opencode_profile.git
cd opencode_profile
```

### 2. Create machine identity (one-time)

```bash
# macOS/Linux
./install/init-machine.sh

# Windows
powershell -ExecutionPolicy Bypass -File .\install\init-machine.ps1
```

This writes a local `.opencode-machine.json` with a unique machine ID (e.g. `macbook-air-m1`).

### 3. See which projects exist

```bash
cat projects/registry/projects.json
```

Currently tracked projects:

| ID | Domain | Status |
|---|---|---|
| `analysic-data` | data | active |
| `explore-CAN-message-motor-voltage` | data | active |

### 4. Add your machine paths

Each project needs a local path on your machine. Edit `projects/registry/projects.json`:

```json
"machine_paths": {
    "WIN-HYPERV-1": "C:\\local\\analysic-data",
    "<YOUR-MACHINE-ID>": "/Users/you/projects/analysic-data"
}
```

### 5. Clone code repos

Navigate to each path you set above and clone the project code repo.

> If a project has `"repo_url": ""`, the code repo does not exist yet. Create it when ready.

### 6. Activate projects for this machine

```bash
./install/activate-project-manager.sh analysic-data
./install/activate-project-manager.sh explore-CAN-message-motor-voltage
```

### 7. Run first full session

```bash
./install/start-session.sh --mode full
```

This verifies:
- Workspace repo is up to date
- All active project paths exist
- Git repos are on the correct branch
- No dirty or unpushed changes

After the first run, use `quick` mode for daily sessions:

```bash
./install/start-session.sh
```

## Operating model

- `1 project = 1 Jira Epic`
- `Weekly report day = Friday`
- `Jira` is the execution and short-doc system
- `Notion` is the project summary and narrative system
- `orchestrator` is the primary orchestration-only agent
- `report-agent` generates drafts only; you review before posting
- `team workspace` is the operational control plane for all active projects

## Team workspace model

This repo is the central team workspace. It tracks:

1. Shared agent definitions and workflows.
2. Per-project operating homes under `projects/<domain>/<project>/`.
3. Session rituals for multi-machine work.
4. Workspace and code-repo freshness checks before each session.
5. Project lifecycle state:
   - `planned`
   - `active`
   - `paused`
   - `done`
   - `archived`
   - `deleted`

Use `archive` for completed projects. Use `delete` only for invalid, duplicate, or sandbox projects.

## Agent architecture

1. `orchestrator`
   - Orchestration only
   - Chooses specialist agents
   - Keeps only short-form context and final decisions

2. `explore-agent`
   - Read-only project discovery
   - Maps structure, entry points, boundaries, and relevant scope

3. `code-agent`
   - Implementation only
   - Makes the smallest correct changes for the scoped task

4. `review-agent`
   - Code and architecture review
   - Can propose architecture changes
   - Architecture changes require owner approval before implementation

5. `qa-agent`
   - Report-only validation
   - Separate modes from day one:
     - `data`
     - `web`
     - `iot`

6. `report-agent`
   - Weekly reporting drafts for Jira and Notion

## Registry and control plane

The workspace keeps both human-readable and machine-readable state:

1. `projects/registry/projects.json`
   - Source of truth for scripts.
2. `projects/registry/projects-index.md`
   - Human dashboard of all tracked projects.
3. `projects/registry/active.md`
   - Active and paused workset.
4. `projects/registry/archived.md`
   - Completed and archived work.
5. `projects/registry/now-working.md`
   - Current session focus.
6. `projects/registry/report-due.md`
   - Reporting queue.
7. `projects/registry/machine-sync.md`
   - Last freshness snapshot generated by scripts.

## Session control

Every work session should start with a freshness check.

Windows:

```powershell
powershell -ExecutionPolicy Bypass -File .\install\start-session.ps1
```

macOS/Linux:

```bash
./install/start-session.sh
```

This checks:

1. The `opencode_profile` repo state.
2. The current machine identity.
3. All active project paths from the registry in `quick` mode.
4. Branch, dirty state, and ahead or behind state where Git is available.
5. Projects that are missing a machine path or are not yet Git-managed.

Use `full` mode on first run or for audit:

Windows:

```powershell
powershell -ExecutionPolicy Bypass -File .\install\start-session.ps1 -Mode full
```

macOS/Linux:

```bash
./install/start-session.sh --mode full
```

At the end of a session:

1. Update project handoff or decision notes if needed.
2. Commit and push `opencode_profile` if operational state changed.
3. Commit and push code repos as appropriate.

See `workspace/sessions/start-session.md`, `workspace/sessions/first-run.md`, and `workspace/sessions/end-session.md`.

Initialize a machine identity once per machine before the first session:

Windows:

```powershell
powershell -ExecutionPolicy Bypass -File .\install\init-machine.ps1
```

macOS/Linux:

```bash
./install/init-machine.sh
```

## Recommended workflow

1. Create a Jira Epic for each project.
2. Create one Notion page for each project.
3. Create the project home with `install/new-project-home.ps1` or `install/new-project-home.sh`.
4. Copy the OpenCode scaffold into each code project root.
5. Set the team project ref inside the code workspace `.opencode/agents/orchestrator.md`.
6. Run the execution flow through specialist agents.
7. Run the weekly report flow every Friday.

For a fast startup flow, use `workflows/new-project-checklist.md` and `workflows/new-project-home-checklist.md`.

## Execution flow

1. `orchestrator -> explore-agent`
   - Use when the project is unfamiliar or the task scope is unclear.

2. `orchestrator -> code-agent`
   - Use after the task scope and target files are clear.

3. `orchestrator -> review-agent`
   - Use after meaningful code changes.
   - Review findings may include architecture improvement proposals.

4. `orchestrator -> qa-agent`
   - Use after review to validate behavior and regression risk.
   - Pick the project mode: `data`, `web`, or `iot`.

5. `orchestrator -> report-agent`
   - Use on Friday or before stakeholder updates.

## Per-project OpenCode scaffold

Copy these files into each project code workspace when it is initialized:

```text
project-root/
  opencode.json
  .opencode/
    agents/
      orchestrator.md
      explore-agent.md
      code-agent.md
      review-agent.md
      qa-agent.md
      report-agent.md
```

Use the scaffold under `scaffolds/opencode-project/` in this repo.

Install it with a script instead of copying by hand:

Windows:

```powershell
powershell -ExecutionPolicy Bypass -File .\install\install-project-scaffold.ps1 -ProjectPath "C:\path\to\project"
```

macOS/Linux:

```bash
./install/install-project-scaffold.sh /path/to/project
```

After installation, add the project operating context to `.opencode/agents/orchestrator.md`:

```md
Project operating context:

1. Team project ref: `projects/data/analysic-data`
2. Domain: `data`
3. Current focus: <fill for this project>
```

### Scaffold rules

1. `orchestrator` is the default primary agent.
2. All agents use `opencode/deepseek-v4-flash-free`.
3. `orchestrator` can call specialist agents through `task` permission.
4. `orchestrator` is denied direct file edits.
5. Specialist permissions enforce role separation.

## Approval gate

1. `review-agent` may propose architecture changes.
2. The proposal must be classified as either:
   - `required fix`
   - `recommended improvement`
3. The owner must approve architecture changes before `code-agent` implements them.
4. `qa-agent` never fixes code directly.

## Weekly reporting flow

1. Open the project home under `projects/<domain>/<project>/`.
2. Read `profile.md` and `reporting/config.json`.
3. Read the linked Jira Epic and child issues.
4. Read recent repo activity and local project state.
5. Use `agents/report-agent.md` with `workflows/report-prepare.md` and `workflows/report-weekly.md`.
6. Produce:
   - one Jira weekly comment draft
   - one Notion weekly toggle draft
7. Save the draft under `reporting/history/drafts/YYYY-MM-DD.md`.
8. After manual posting, save a published snapshot under `reporting/history/published/YYYY-MM-DD.md`.

## Project lifecycle operations

Create a new project home:

```powershell
powershell -ExecutionPolicy Bypass -File .\install\new-project-home.ps1 -ProjectId "my-project" -Domain web -LocalPath "C:\local\my-project"
```

macOS/Linux:

```bash
./install/new-project-home.sh my-project web /path/to/project
```

Archive a completed project:

```powershell
powershell -ExecutionPolicy Bypass -File .\install\archive-project.ps1 -ProjectId "my-project"
```

Delete an invalid or sandbox project:

```powershell
powershell -ExecutionPolicy Bypass -File .\install\delete-project.ps1 -ProjectId "my-project" -Reason sandbox -Force
```
